# Plan: V2 1.1 e-invoice signed QR verification

Planned 2026-10-14 (ECC planner, from research made that day). Parent plan:
`docs/plans/v2-market-leader.md`. Six small PRs, each deployable alone, tests first.

## Why

An IRP-signed QR is the only evidence on an invoice that a third party (the GST invoice
registration portal) vouches for: seller and buyer GSTIN, invoice number, date, total, item
count and IRN, signed RS256. Checking it offline against the IRPs' public keys turns "the
values look consistent" into "these values were registered with GST". No competitor found in
the 2026-10-14 research does this.

## Facts it rests on (research 2026-10-14)

- QR text: compact JWS, header `{"alg":"RS256","kid":<hex SHA-1 of the signing certificate>,
  "typ":"JWT","x5t":<the same, base64url>}`; payload `{"data":"<JSON string>","iss":"NIC"}`;
  data: SellerGstin, BuyerGstin, DocNo, DocTyp (INV/CRN/DBN), DocDt (dd/mm/yyyy), TotInvVal,
  ItemCnt, MainHsnCode, Irn (64 hex), sometimes IrnDt. Verified on NIC's sandbox sample.
- Six IRPs, each with its own signing key (NIC1, NIC2, and private IRPs since 2023: IRIS,
  Clear, Cygnet, EY). Keys rotate every 1-2 years; old keys stay needed; an expired
  certificate must not fail a signature made while it was valid.
- Known key sources: Vayana GSP documentation (NIC1, NIC2 production; third-party published),
  IRIS's portal (einvoice6.gst.gov.in/content/public-keys/). Others not found yet.
- Decoder: zxing-cpp (Apache-2.0, wheels, no system libraries) reads the ~900-character QR
  at >= 2.2 px per module (300 dpi render); OpenCV failed blurred cases.
- Cancelled IRNs cannot be detected offline.

## Phases (one PR each)

1. **Library** `src/docforge/einvoice/jws.py`, `keys.py`, `keys/manifest.json`:
   strict parsing (<= 4096 chars, three segments, RS256 only, `data` <= 2 KB, typed
   `SignedInvoice`), `verify(qr, keyring)` -> verified / bad_signature / unknown_key /
   malformed / not_einvoice (UPI and other QRs). Manifest per key: name, IRP, environment,
   source URL, fetched date, sha256 (checked at load), kid, `confirmed_by_real_qr`,
   not_after. Sandbox keys never load in production; test keys are never bundled.
   `cryptography` added explicitly.
2. **Decoder** `src/docforge/einvoice/scan.py` in its own isolated child process (as the
   parser: spawn, secrets stripped, time and memory limits, recycled), pages 1, last, 2-5,
   300 dpi then 450 dpi on page 1; caps on symbols and text. Not inside the parser child:
   that would change cached and replayed parses.
3. **Storage and worker**: migration (after 0038) `einvoice_checks` per document version -
   tenant RLS, append-only, erased with the account, status, page, the JWS, key name / IRP /
   kid / sha256 / source / confirmed, issuer, signed fields, decoder version. The worker scans
   invoices (PDFs and renditions) before reading; any failure is `unreadable`, never a failed
   reading. Audit entry with status and IRP only.
4. **Trust rules** `src/docforge/trust/einvoice_rules.py`, passed to `assess` as extra rules
   on first reading and on every reassessment in review: signature (error), seller GSTIN,
   buyer GSTIN (skipped for URP), invoice number, date, grand total within 1.00 (errors, only
   when verified); line count, document type, IRN printed on the page (warnings). No QR, a
   UPI QR or an unreadable one adds nothing. New eval `einvoice` with a test-only key and its
   gate floors; existing reports must not change.
5. **API**: `einvoice` on the review and assessment responses (never the raw JWS); OpenAPI
   and the frontend handover regenerated.
6. **Web**: a banner on the review screen - "Verified e-invoice: signed by IRP NIC-1;
   seller GSTIN, invoice number, date and total match", or what disagrees, or "QR signature
   invalid"; "key not yet confirmed against a real QR" while unconfirmed; nothing when there
   is no QR.
7. **Real keys** (needs the owner's invoices): `python -m docforge.einvoice check <pdf>...`
   on real NIC1 / NIC2 / IRIS invoices; mark each key confirmed and record its kid; drop any
   key that never verifies a real QR.

Kill switch: `DOCFORGE_EINVOICE_ENABLED=false` skips scanning and rules.

## Decisions taken (defaults; the owner can change them)

| Question | Taken | Why |
|---|---|---|
| A QR signed by a key DocForge does not hold | warning, not a failure | an error would send every invoice from an IRP we hold no key for to review |
| Grand total tolerance | 1.00 | round-off on Indian invoices; to be checked on the real set |
| Deleting a document | the check stays hidden with the document, like its extraction; erased with the account | the same rule as every other per-version record |
| Decoder memory | 512 MB child, recycled | short-lived; worker headroom next to Docling checked before deploy |

## Reviews

security-reviewer on PRs 1-3 (crypto, untrusted pixels into a native decoder, RLS and
erasure), database-reviewer on 3, python-reviewer on 1-5, typescript-reviewer on 6.

## Done when

- A tampered or forged QR sends the invoice to review with a plain reason; a valid one with
  matching fields shows "Verified e-invoice".
- No QR, a UPI QR or a decode failure changes no existing outcome and never fails a reading.
- Sandbox and test keys cannot be trusted in production.
- Rows are tenant-isolated and erased with the account.
- Every existing gate floor holds; the new `einvoice` gate passes.
