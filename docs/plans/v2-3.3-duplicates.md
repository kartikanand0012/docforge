# Plan: V2 3.3 duplicate bills

## Why

The same bill entered twice is paid twice. Uploading the identical file is already one document
(same sha256), but a second scan, a photo, an emailed copy or a reprint is a new file. Chemists
and distributors check this by hand today; it is the check they notice first.

## What counts as a duplicate

An **invoice** whose bill was already received in the same workspace, as another live invoice
document uploaded **earlier**:

1. **Same IRN** - both have a verified e-invoice QR with the same IRN (`einvoice_checks`,
   status verified, `evidence.invoice.irn`). The strongest: the portal issues one IRN per bill.
2. **Same seller GSTIN and invoice number** - each as the reading has it, after corrections.
   Invoice numbers are compared without case or spaces ("NVM/26-27/32001" = "nvm/26-27/ 32001");
   "/" and "-" count. A GSTIN is the bill's issuer, and a seller's number is unique for a year:
   two bills from one seller with one number are the same bill.

Not a duplicate: the same document read again (its own versions), a purchase order, a deleted
document, or an earlier one that a reviewer **rejected** (the second may be the corrected
resend). Only the later of the two is flagged: the first one received is the original.

## Behaviour

- Review: the later invoice gets a blocker - "it may be a duplicate of {filename}, which has
  the same IRN" (or "the same seller GSTIN and invoice number"). It waits in the queue and
  approving it needs an override reason, like every other blocker.
- `ReviewOut.duplicates`: `[{document_id, filename, matched_on: "irn" | "seller_and_number"}]`,
  so the screen can link to the earlier bill.
- Computed live on each review read (like the order match), so it follows corrections on either
  side, a deletion, and a rejection, with nothing to keep in sync and nothing to backfill: bills
  read before this change are found too.

## How (one PR backend, one PR web)

1. **Lookup** `src/docforge/trust/duplicates.py`: candidates by index, then compared in Python
   on each candidate's effective values (its extraction with its latest corrections):
   - by number: newest versions whose extracted invoice number, or a correction of it, has the
     same key; at most 20 candidates;
   - by IRN: newest versions with a verified check of that IRN.
2. **Migration 0040**: expression indexes only - extractions `(tenant_id, invoice key)`,
   corrections `(tenant_id, key of new_text) WHERE path = 'invoice_no'`, einvoice_checks
   `(tenant_id, evidence.invoice.irn) WHERE status = 'verified'`. No new table, no data change.
3. **Review state**: `duplicates` on `_State`, a blocker per duplicate, `ReviewDetail` and
   `ReviewOut.duplicates`; OpenAPI and the handover.
4. **Web**: blocker labelled "Possible duplicate" linking to the earlier bill.

## Tests (first)

Same IRN; same seller and number with spacing and case changed; a correction on either side
that makes or breaks the match; another seller with the same number; the earlier one deleted
or rejected; a purchase order with the same number; the earlier one not flagged; another
workspace's bill never seen; reprocessing a document does not flag itself; the queue lists it
with the reason; approving needs an override.
