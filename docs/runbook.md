# Runbook: the public demo on AWS

One arm64 EC2 host in its own VPC runs the Compose stack in `deploy/` (Postgres, API, worker,
review app, Caddy for HTTPS). Originals go to a private S3 bucket and are deleted after 7 days. The demo runs on the
recorded synthetic documents, so it needs no model key and has no model cost. Terraform in
`infra/` creates everything. Nothing here has been applied yet: it needs an AWS account.

Estimated cost in ap-south-1, about $40 a month if it runs all month:
- **t4g.large on demand:** about $33. That is $0.0448 an hour per third-party price trackers (cloudprice.net, checked 2026-10-03), not AWS itself.
- **Public IPv4 address:** about $3.65. AWS charges $0.005 an hour for every public IPv4 address, attached or not.
- **40 GB of gp3 storage:** a few dollars.
- **S3 and ECR:** cents at this size.

Confirm in the AWS pricing calculator before applying. T4g instances run in "unlimited" CPU-credit mode by default, so sustained heavy CPU (live OCR on long scans) costs extra. The demo replays recorded documents and stays well below its baseline.

The budget alarm warns at 80% and 100% of `monthly_budget_usd` (default $50).

## What you need first

- An AWS account and an administrator profile for the AWS CLI (`aws configure sso` or keys),
  only on your machine.
- Terraform 1.9 or later, or the `hashicorp/terraform` image.
- A private S3 bucket for Terraform state, with versioning and encryption on. State holds the
  generated database passwords.
- Optional: a domain. Without one the demo is served at `<elastic-ip>.sslip.io` with a real
  Let's Encrypt certificate.

## First deployment

1. Fill in the `backend "s3"` block in `infra/versions.tf` with your state bucket.
2. `cp infra/terraform.tfvars.example infra/terraform.tfvars` and set `alert_email`,
   `region`, and for now `image_tag = "bootstrap"`.
3. Create the image repositories and the deploy role first:
   ```bash
   cd infra
   terraform init
   terraform apply -target=aws_ecr_repository.app -target=aws_iam_role_policy.deploy
   ```
4. In GitHub, add the secret `AWS_DEPLOY_ROLE_ARN` (from `terraform output deploy_role_arn`)
   and the variable `AWS_REGION`. Run the **Images** workflow on `main`. It pushes
   `docforge-app:<sha>` and `docforge-web:<sha>`.
5. Set `image_tag = "<that sha>"` in `terraform.tfvars` and `terraform apply`. The host fetches
   `deploy/` from its read-only bucket and reads its settings from three SSM parameters
   (`/docforge/demo/compose`, `app`, `owner`). It then pulls the images, migrates, seeds the
   demo and starts. That takes about ten minutes.
6. Confirm the email subscription AWS sends to `alert_email`.
7. Open `terraform output url` in a clean browser. The sign-in page shows the demo account.
   It is a reviewer: it can read, search, correct and sign, but it cannot upload, make keys or
   set up webhooks. Wrong PINs never lock it, because its PIN is public.

## Redeploying a new version

1. Run the **Images** workflow on the commit to deploy.
2. `terraform apply -var image_tag=<sha>` (updates the settings parameter).
3. Run the bootstrap again on the host:
   ```bash
   aws ssm send-command --instance-ids "$(terraform output -raw instance_id)" \
     --document-name AWS-RunShellScript \
     --parameters 'commands=["/opt/docforge/bootstrap.sh"]'
   ```
   It pulls the new images, migrates and restarts. Rolling back is the same with the previous
   sha (migrations only add; an older version runs against a newer schema).

## Every day

- 02:30 UTC: the demo resets itself (`deploy/reset-demo.sh`): visitors' corrections and
  signatures go, the synthetic documents come back.
- Every five minutes: `deploy/ops-check.sh` reports 0, 1 or 2 to CloudWatch. Two critical
  reports in fifteen minutes, or none at all, email you. So does a failed instance status check.
- Logs: `aws ssm start-session --target <instance id>`, then `cd /opt/docforge && docker compose logs`.

## Where the secrets are

| File on the host | Who reads it | Holds |
| --- | --- | --- |
| `.env` | Compose | Images, domain, the public demo PIN |
| `app.env` | API, worker | The restricted database login, the app's S3 key, the webhook key |
| `owner.env` | Postgres, the one-shot `admin` service | The database owner's password |

The API and worker never hold the owner's password, and they cannot reach the host role:
the instance metadata hop limit is 1. All three files are root-only.

## Rotating secrets

The database passwords, the webhook key, the app's S3 key and the demo PIN are all generated by Terraform. To rotate one:

1. `terraform apply -replace=<resource>`, using one of:
   - `random_password.postgres`, `random_password.app_login` or `random_password.webhook_key`;
   - `aws_iam_access_key.app`;
   - `random_integer.demo_pin`.
2. Run the redeploy above. It rewrites the files and restarts the stack.

The Postgres owner password is set when the volume is first created. Rotating it also needs `ALTER USER docforge PASSWORD ...` on the host.

## Turning it off

`terraform destroy` removes everything except the originals bucket, which is protected
(`force_destroy = false`): empty it first with `aws s3 rm --recursive s3://<bucket>` if you
mean to delete it.

## Not covered here

- No backups: the demo's data is synthetic and re-seeded every night. A real deployment needs
  RDS (or snapshots of the volume) and point-in-time recovery.
- One host, one zone: a real deployment needs at least two, behind a load balancer.
- Live extraction: set `GEMINI_API_KEY` and `PIPELINE_FACTORY=docforge.wiring:build_pipelines`
  in the settings parameter, and size the host for the parser (`PARSER_MAX_RSS_MB`).
