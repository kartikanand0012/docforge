# DocForge - Part A: Production problems in document extraction and RAG-over-documents

Compiled 2026-10-01 from web research. Evidence grading: [V] = read directly from the cited page this session (via summarising fetch); [S] = from a search-result snippet only; [U] = unverified / vendor claim / my inference. Many sources are vendor blogs or Medium posts (marketing bias). Benchmark numbers are as reported by their authors and should be re-measured on pharma documents. Model names in some sources (e.g. "Mistral OCR 4", "GPT-4.5", "Claude Opus 4.8") are quoted as written there and were not independently checked.

## 3. Vision-LLM vs classic OCR + layout

Numbers as reported (check dates and splits before quoting):
- OmniDocBench v1.6 (aggregator summary): PaddleOCR-VL 0.9B 96.34, MinerU2.5-Pro 1.2B 95.75, GLM-OCR 0.9B 95.22, versus Qwen3-VL-235B 89.78. Small dedicated doc models beat large general VLMs. [S] https://blog.roboflow.com/best-open-source-ocr-models/ ; original benchmark https://arxiv.org/abs/2412.07626
- olmOCR-Bench subset (40 docs, 223 tests; independent repo, author flags it as directional): Mistral OCR 4 74.9% overall, Qwen3-VL 235B 72.6, GPT-4.5 71.3; tables 94.3 / 90.0 / 92.9; reading order 73.3 / 53.3 / 56.7; Marker 55.2 overall, Docling 37.7. Frontier VLMs return no bounding boxes or per-word confidence; dedicated parsers give boxes but read 20-45 points worse. [V] https://github.com/ukanwat/ocr4-structure-benchmark ; vendor post https://mistral.ai/news/ocr-4/ [S]
- ParseBench (LlamaIndex-affiliated authors [U]): AWS Textract, Google DocAI, Azure DI, Claude, GPT-5, Gemini 3 Flash, Qwen3-VL, LlamaParse, Reducto, Docling, MinerU compared; weak spots are complex tables, charts, formatting, grounding. Fetch summary gave vague headline numbers; read the paper for exact scores. [V-partial] https://arxiv.org/pdf/2604.08538
- Cost per 1,000 pages (aggregator summaries, verify against official pricing pages): Textract text $1.50, Tables $15, Forms $50; Google DocAI $1.50 OCR up to $30 custom extractor; Mistral OCR 4 $4 (batch $2). Self-hosted PaddleOCR-VL ~$0.09/1k pages claimed. [S] https://aws.amazon.com/textract/pricing/ ; https://aiproductivity.ai/blog/document-ai-cost-comparison/ ; [V] intuitionlabs link above for $0.09.
- Latency: Docling 1.26 s/page, LlamaParse ~6 s/page (blog; [U]). Docling tables 97.9% (blog; [U]). https://tianpan.co/blog/2026/04/17/document-ai-production-pdf-pipeline
- Trade-off summary: VLMs/OCR-VLMs win on layout-heavy and messy docs but lack provenance and can hallucinate digits; classic OCR + layout gives boxes and per-word confidence but weak on complex tables; hybrid (OCR for text/boxes, VLM for structure/review, router by page complexity) is what vendors converge on. https://llms.reducto.ai/hybrid-architecture-agentic-ocr-deep-dive

## 4. Confidence scoring, human review, provenance

- Symptom: model self-reported confidence is poorly calibrated; no way to know which fields to review. Practice: field-level confidence from OCR word confidences plus validation signals (format, cross-field, agreement across two extractors/runs); per-field thresholds by business risk (example: amount >= 0.92, notes >= 0.80; generic 0.75-0.85 straight-through). Thresholds are rules of thumb, tune on your own golden set. [S] https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/document/enrichments ; https://theneuralbase.com/ocr-for-ai/learn/advanced/field-level-accuracy-for-forms/ ; [V] tianpan link (99%+ effective accuracy with HITL when AI alone is 92-95%).
- Provenance: store page number plus bounding box per extracted value; Azure Content Understanding documents "grounding" (page + bbox) used to highlight source in review UI. [S] Azure link above. Because frontier VLMs return no boxes (see section 3), obtain boxes from OCR/layout and align the extracted value to an OCR span, rejecting values that cannot be matched (my design inference [U]).
- Audit trail for reviews: timestamps, reviewer identity, original vs corrected value. [V] tianpan link.

## 5. Chunking and retrieval

- Symptom: chunk lacks context ("revenue grew 3%" without company/period). Mitigation: contextual retrieval (prepend LLM-generated context). Anthropic: top-20 failure rate 5.7% -> 3.7% (contextual embeddings), 2.9% (plus BM25), 1.9% (plus reranking); one-time cost $1.02 per million document tokens with prompt caching. [V] https://www.anthropic.com/news/contextual-retrieval
- Pure dense search misses exact identifiers (batch numbers, SKUs, CAS numbers); add Postgres full-text/BM25 (GIN tsvector, or pg_textsearch) and fuse with RRF in one SQL statement. [S] https://dev.to/gabrielanhaia/hybrid-search-in-100-lines-bm25-pgvector-with-rrf-merge-58cn ; https://www.tigerdata.com/blog/introducing-pg_textsearch-true-bm25-ranking-hybrid-retrieval-postgres
- Parsing corrupts text before the chunker runs (tables, scans, multi-column). Chunk tables as units with header repeated; keep section/heading path as metadata. [V] https://github.com/landedjobs/rag-engineer-interview-questions
- Wrong answer though right doc exists: debug in order parse -> chunk -> retrieve -> rerank -> generate (framing from interview guide). [V] https://prachub.com/resources/ai-engineer-interview-questions-2026-rag-agents-evals-and-production-systems

## 6. pgvector: when enough, where it breaks

- Filtered search silent recall collapse: with hnsw.ef_search=40 and a filter matching 10%, ~4 rows survive; LIMIT 10 returns fewer. Fix: pgvector 0.8 `hnsw.iterative_scan = relaxed_order|strict_order`, cap with `hnsw.max_scan_tuples` (default 20,000); pre-filter via CTE for very selective filters; raise ef_search. [V] https://clickhouse.com/resources/engineering/scale-vector-search-postgres ; GitHub reports of "fewer than top_k, often zero" for small-share tenants [S] https://github.com/noctua84/nescio-memory/issues/12
- Scale bands (vendor article, rough): ~1M vectors easy; ~10M needs quantization (halfvec/binary) and partitioning; ~100M evaluate alternatives; >1B pure Postgres rarely simplest. 1536-d fp32 ~6 KB raw, ~20-25 KB per vector with HNSW overhead (that source's figure). Dedicated vector DB when sub-20 ms p99 mandatory. Memory eviction of the HNSW graph turns ms into seconds; MVCC dead tuples from frequent re-embedding degrade recall. 2,000-dim limit for `vector` index, halfvec to 4,000. [V] ClickHouse link (ClickHouse sells managed Postgres: bias).
- Multi-tenant: partition by tenant or partial HNSW per large tenant; flat scan on small partitions gives 100% recall; RLS with `FORCE ROW LEVEL SECURITY` and transaction-local `SET app.tenant_id`; ~20% overhead with RLS (single blog claim, [U]); do not put tenant_id in a multicolumn HNSW; beware SECURITY DEFINER functions bypassing RLS. [S] https://render.com/articles/multi-tenant-rag-postgresql-pgvector ; https://dev.to/virginiamwega2svg/your-where-clause-is-not-a-security-boundary-multi-tenant-rag-with-pgvector-rls-28fk ; https://pradeepbhandari.com/blog/pgvector-multi-tenancy-postgresql-rls-guide
- Verdict for DocForge: pgvector is sufficient up to low millions of chunks per cluster with tenant partitioning; document a migration path (CDC to a dedicated vector DB) rather than building it.

| # | Symptom | Root cause | Mitigation | Source |
